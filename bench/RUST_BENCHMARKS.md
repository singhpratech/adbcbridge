# Per-database benchmarks, from Rust

Generated by `bench/rust/run.sh` (see `bench/rust/src/main.rs`); one row per
database, each rewritten in place the next time that database is run, so the rows
are not all from the same day — the sixteen from `sqlite` and `mariadb` down were
taken on 2026-08-24, the rest on 2026-08-23. Table
`(id int32, val float64, txt "row-%012d" utf8, dt date32)`, one database per run,
every number the median of 3 timings after a warmup. All rates are rows/s; higher
is better.

| Column | What it measures |
|---|---|
| **ADBC ingest** | 10,000 rows through `libadbc_driver_odbc.so` and the Rust ADBC driver manager: bulk ingest in `create` mode, autocommit off, one commit, DDL + data + commit timed together and the row count verified afterwards. |
| **odbc-api ingest** | the same rows through the [`odbc-api`](https://crates.io/crates/odbc-api) crate: a prepared `INSERT ... VALUES (?, ?, ?, ?)` with array-bound parameters (`ColumnarBulkInserter`, 8192 rows per execute), autocommit off, one commit. The table is created by an empty ADBC ingest first, so both paths write into identical DDL. |
| **Ingest ×** | ADBC ingest over odbc-api ingest. |
| **ADBC fetch** | `SELECT id, val, txt, dt` of 100,000 rows drained into Arrow `RecordBatch`es through the bridge. |
| **odbc-api fetch** | the same `SELECT` read straight from the ODBC driver into a column-wise row-set buffer (`ColumnarDynBuffer`, 8192 rows), no Arrow — the raw ODBC floor for this read. |
| **arrow-odbc fetch** | the same `SELECT` through the [`arrow-odbc`](https://crates.io/crates/arrow-odbc) crate's `OdbcReaderBuilder`, which builds Arrow `RecordBatch`es from those same ODBC buffers. |
| **Fetch ×** | ADBC fetch over odbc-api fetch. |

Native delegation is switched off (`adbc.odbc.delegate=never`), so every row really
travels over ODBC. Servers run locally in Docker, so the numbers reflect the ODBC
driver plus the database, not a network — and they move with whatever else is running
on the host, so read them as ratios rather than absolutes.

A `—` is a step that did not finish; `bench_rs` prints the reason on stderr. The one
that is not transient is **arrow-odbc on Db2**: the `clidriver` `libdb2.so` is built
with a 32-bit `SQLLEN`, which makes `odbc-api` panic when it describes a column
(IBM's 64-bit `libdb2o.so` ships without its dependent libraries here, so it cannot
stand in). The bridge detects that layout itself — `adbc.odbc.sqllen_32bit` — and
reads the same result set fine. MySQL Connector/ODBC needs the same
`LD_PRELOAD=/lib/x86_64-linux-gnu/libstdc++.so.6` the compat matrix documents in
[`tests/compat/README.md`](../tests/compat/README.md).

Three rows do not read the way the paragraph above describes. **oracle**'s fetch
columns were `—` because the read used to *crash the process*: any row-array fetch
of a character column segfaulted inside Oracle's own `libsqora.so.23.1`
(`bcoReturnColData` under `SQLFetch`). The driver now settles the rowset before the
first fetch and never moves it on SQORA, and reads a column with no real declared
width — the `txt` column here, which generated ingest DDL spells `CLOB` — with
`SQLGetData`, one row at a time. All three fetch columns are numbers again, and
all three are an order of magnitude below what the same four columns read from a
server whose strings are ordinary `VARCHAR`: that is the price of the row-at-a-time
path, and `odbc-api` and `arrow-odbc` pay it too. **monetdb**'s `odbc-api` and
`arrow-odbc` columns are `—` because that crate cannot open the DSN at all
(`SQLDriverConnect` → `IM005 … Driver's SQLAllocHandle on SQL_HANDLE_DBC failed`),
though the bridge and pyodbc both connect through the same unixODBC; the monetdb
row also needs `ADBC_BENCH_AUTOCOMMIT=1`, because MonetDBODBClib's `SQLEndTran` is
a no-op and an autocommit-off ingest leaves nothing behind. And **db2**'s
`odbc-api`/`arrow-odbc` columns return numbers rather than panicking, but the
32-bit `SQLLEN` they are reading through has not changed, so they are not
throughput to compare against the ADBC column. **informix** reaches the same
`clidriver` `libdb2.so`, and its `arrow-odbc` column is `—` for that reason:
`Failed to retrieve data type from ODBC driver. The SQLLEN could not be converted
to a 16 Bit integer`.

Six rows were not measured with autocommit off, because their server or driver
cannot run that workload at all, and were taken with `ADBC_BENCH_AUTOCOMMIT=1`
instead — **sqlite**, **databend**, **doris**, **starrocks**, **ydb**, and
**influxdb3**, which fails either way. In that mode the bridge batches the stream
into one transaction itself and the benchmark never calls `SQLEndTran`, and the
`odbc-api` ingest column goes `—` with it: the comparison writes into a
transaction it then cannot verify (`wrong row count 0 != 10000`). **ydb** also
had `ADBC_BENCH_NO_NATIVE=1` set, so both of its comparison columns are empty; on
the run without it the row-at-a-time `odbc-api` insert alone overran a 600-second
cap. `bench/LANGUAGE_BENCHMARKS.md` records what each of these fails with, and
which of them the other four language bindings reproduce.

Four of the databases below have no ADBC column at all. **cratedb** and **spanner**
refuse the generated ingest DDL (``Type `date` does not support storage`` and
`Type <int4> is not supported; use bigint or int8 instead`), **ignite** refuses any
`CREATE TABLE` without a primary key, and **mongodbbi**, **flightsql** and
**dremio** refuse `SQLSetConnectAttr(SQL_ATTR_AUTOCOMMIT, OFF)` so the connection
never opens. **duckdb** has an ingest but no fetch: the entry connects with
`Database=:memory:`, so the table the ingest wrote is gone from the next
connection. [`LANGUAGE_BENCHMARKS.md`](LANGUAGE_BENCHMARKS.md) quotes each of these
in full.
